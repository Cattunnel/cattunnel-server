# CONNECT в CatTunnel: что endpoint меняет относительно TrustTunnel

Документ описывает транспорт CONNECT (HTTP/2 CONNECT поверх TLS) endpoint'а
CatTunnel в выпуске 1.5.9.5. Для каждого места сказано, что делает upstream
TrustTunnel, что делает форк и как работает изменённая часть. Это не история.
Остальные протоколы описаны отдельно: [NineLives](ninelives.md) и
[CatTail](cattail.md). Все места, где форк уходит от upstream, собраны в
[upstream-divergence.md](upstream-divergence.md). Английский перевод:
[connect.en.md](connect.en.md); при расхождении верен русский текст.

База. Форк идёт от upstream TrustTunnel `v1.3.0-beta.2` (merge-base
`48f424c`). Содержимое upstream `v1.3.1` включено (TRUST-773, TRUST-805,
TRUST-826). Пробное слияние `v1.3.1` даёт конфликты только в `CHANGELOG.md` и
`lib/tests/subscription.rs`. Клиентская сторона того же транспорта описана в
документе `connect-client.md` репозитория ядра клиента.

## 1. Что здесь называется CONNECT

Клиент открывает TLS до endpoint'а, договаривается об `h2` и на каждое
туннелируемое TCP-соединение шлёт один HTTP/2-запрос `CONNECT host:port` с
`Proxy-Authorization: Basic`. Ответ `200` превращает поток в канал байтов.
Три authority особые и не открывают TCP-соединение: `_check` (проверка живости),
`_udp2` (мультиплексор UDP), `_icmp` (мультиплексор ICMP).

```text
 client                                         endpoint
   |                                               |
   |== TCP 443 ===================================>|  accept, nodelay, keepalive
   |== TLS ClientHello (SNI, ALPN h2) ===========>|  read hello, client_random
   |<=========================== ServerHello ... ==|  SNI picks the host type
   |== h2 SETTINGS ===============================>|
   |== HEADERS CONNECT example.org:443 ===========>|  stream 1, Basic auth
   |<========================== HEADERS 200 =======|  headers of section 3.1
   |== DATA ======================================>|  bytes to the destination
   |<========================================= DATA |  frames of 4096 bytes max
   |== HEADERS CONNECT _check ====================>|  keepalive (section 6)
   |<========================== HEADERS 200 =======|  stream ends at once
```

Рисунок 1. Один туннель CONNECT внутри TLS-соединения. Много таких потоков
идут в одном TLS-соединении, а клиент держит несколько TLS-соединений (пул).

## 2. Путь соединения внутри endpoint'а

```text
 TCP accept (core.rs)                     CatTail listener (cattail.rs)
      |                                        |  admission, then inner bytes
      v                                        v
   +--------------------------------------------------+
   | Core::serve_stream: TlsListener::listen          |
   |  - join ClientHello split over TLS records       |
   |  - take client_random (prefix / auth key check)  |
   |  - count the JA4 fingerprint                     |
   +----------------------+---------------------------+
                          v
   +--------------------------------------------------+
   | TlsDemux::select(ALPN, SNI)                      |
   |  main host -> tunnel channel   h2 or h1 or h3    |
   |  reverse proxy host -> decoy   h1, h2 or h3      |
   |  ping / speedtest hosts -> own handlers          |
   +----------------------+---------------------------+
                          v
   +--------------------------------------------------+
   | HttpDemux::select (per request)                  |
   |  subscription, ping, speedtest, NineLives path,  |
   |  reverse proxy path, otherwise TUNNEL            |
   +----------------------+---------------------------+
                          v
   decoy-only check -> auth (Basic) -> rules -> TCP connect -> pipe
```

Рисунок 2. Слои между сокетом и туннелем. Один и тот же приёмник обслуживает
TCP-листенер и внутренний поток CatTail.

Код: цикл accept и `serve_stream` в `lib/src/core.rs`, чтение ClientHello в
`lib/src/tls_listener.rs`, выбор хоста в `lib/src/tls_demultiplexer.rs`,
маршрутизация запросов в `lib/src/http_demultiplexer.rs`, путь туннеля в
`lib/src/http_downstream.rs`.

## 3. Отличия от upstream

| Тема | Upstream (v1.3.0-beta.2) | Форк (1.5.9.5) |
|---|---|---|
| Ответ `200` на CONNECT | пустой `200` без заголовков | заголовки веб-сервера, случайные id (3.1) |
| Размер кадра DATA к клиенту | сколько разрешает управление потоком | не больше 4096 байт на потоках CONNECT (3.2) |
| Ответы с ошибкой | до v1.3.1 нет `Content-Length` | `Content-Length: 0`, то же изменение, что в upstream v1.3.1 |
| Клиенты, пробовавшие закрытый порт | не моделируются | `decoy_only_ips_file`: VPN отказано, заглушка остаётся (3.4) |
| ClientHello в нескольких TLS-записях | не склеивается | склеивается (3.5) |
| ALPN на хостах-заглушках | только h1 и h3 | h1, h2 и h3 |
| JA4 клиентов | не собирается | считается, отдаётся на листенере метрик |
| Внешний слой | нет | необязательный листенер CatTail ([cattail.md](cattail.md)) |

### 3.1 Правдоподобный ответ 200

Upstream отвечает на CONNECT пустым `200`. Заголовки идут внутри TLS, поэтому
цензор видит только их размер, а пустой ответ одного и того же размера каждый раз
является признаком туннеля. Форк отвечает набором, который шлёт веб-сервер:

```text
 HEADERS (stream N, END_HEADERS, no END_STREAM)
   :status          200
   date             <now, IMF-fixdate>
   server           nginx
   cache-control    no-cache, no-store, must-revalidate
   x-request-id     <hex of 8..40 random bytes = 16..80 characters>
   x-trace-id       <hex of 8..40 random bytes = 16..80 characters>
   (no content-length, no transfer-encoding)
```

Рисунок 3. Ответ на туннельный CONNECT.

Длина каждого id выбирается заново для каждого ответа, поэтому размер ответа не
становится новой константой. RFC 9110, раздел 9.3.6, запрещает `content-length`
и `transfer-encoding` в ответе 2xx на CONNECT: клиент считал бы данные туннеля
против `content-length`. Запрос `_check` получает обычный `200` upstream с
закрытым потоком, а не этот набор.

### 3.2 Кадры DATA по 4096 байт

Загрузка в браузере по HTTP/2 приходит мелкими кадрами DATA. Путь записи upstream
заполняет окно, которое разрешает стек h2 (до размера кадра 16384). Для потока с
методом CONNECT форк режет каждую запись до `min(окно, 4096)`; остальные методы
(заглушка, подписка) сохраняют полный размер.

```text
 upstream:  [ DATA 16384 ][ DATA 16384 ][ DATA 16384 ] ...
 fork:      [4096][4096][4096][4096][4096][4096][4096] ...   (CONNECT only)
```

Рисунок 4. Размеры кадров DATA от сервера к клиенту при скачивании через CONNECT.

### 3.3 Ошибки нулевой длины

Каждый отказ, отправленный через `send_bad_response`, содержит
`Content-Length: 0` и пустое тело (HTTP/1.1, HTTP/2). Это изменение upstream
TRUST-773: форк несёт тот же код и добавляет тесты для CONNECT, decoy-only и
ответов на неверный пароль. Статус неудачной аутентификации задаёт
`auth_failure_status_code` (по умолчанию 407, допустимы 407, 405, 404, 403);
`non_connect_auth_failure_status_code` может задать другой для запросов не-CONNECT.

### 3.4 Сайт-заглушка и decoy_only_ips_file

Соединения к хосту обратного прокси (выбор по SNI) и, на основном хосте, запросы с
путём, начинающимся с `reverse_proxy.path_mask`, идут в обратный прокси сайта-заглушки,
поэтому endpoint отвечает как обычный сайт. `decoy_only_ips_file` называет
текстовый файл: один IP-адрес или сеть CIDR в строке (`#` начинает комментарий).
Адрес клиента из списка по-прежнему получает TLS и сайт-заглушку, но любой
VPN-запрос с него (CONNECT, NineLives, подписка, учётные данные в SNI) получает
ответ как при неудачной аутентификации, даже с верными учётными данными. Файл
перечитывается при смене времени изменения (проверка не чаще раза в 5 секунд);
отсутствующий файл означает пустой список. CatTail встречает такой адрес
молчанием (см. [cattail.md](cattail.md), раздел 3.2).

```text
 request from address A
        |
        +-- A in decoy list?  yes --> answer as failed auth (405/407...), stop
        |                      no
        v
   Basic credentials valid?   no --> failed auth answer
        | yes
        v
   rules, TCP connect, 200 + pipe
```

Рисунок 5. Решение по туннельному запросу. Список предназначен для наполнения
файрволом хоста после того, как адрес пробовал закрытый порт.

### 3.5 ClientHello в нескольких записях

RFC 8446, раздел 5.1, позволяет клиенту разрезать ClientHello на несколько TLS-записей.
Endpoint склеивает фрагменты рукопожатия, пока не придёт всё сообщение, затем читает
`client_random` и считает строку JA4, которая учитывается и отдаётся по `/ja4`
листенера метрик. Разбор upstream брал только первую запись, поэтому ClientHello,
разрезанный по записям, оставлял его ждать байты, которые клиент не пришлёт. Клиентское
ядро 1.5.9.5 режет первую порцию на уровне TCP и отклоняет разрезание TLS-записи
(`-r`) в планах desync, так что склейка обслуживает других клиентов и старые сборки;
комментарий в коде называет anti-DPI CatTunnel источником таких ClientHello.

## 4. Добивка со стороны клиента

Клиент может добавлять случайную добивку (флаг PADDED у HEADERS и DATA, RFC 9113,
раздел 6.1) к первым кадрам каждого потока. Собственного кода для этого в
endpoint'е нет: он полагается на крейт `h2`, который принимает кадры с добивкой.
В этом репозитории нет теста, который шлёт кадры с добивкой; совместимость
держится на RFC. Подробности в `connect-client.md`.

## 5. Пул соединений клиента

Endpoint пул не координирует. Клиент держит от 2 до 4 TLS-соединений и от 24 до 48
потоков на соединение, прежде чем открыть следующее (документ клиента). Endpoint
видит их как обычные h2-соединения с одного адреса. Ограничение числа
h2-соединений на клиента: настройка upstream `default_max_http2_conns_per_client`
(не менялась, по умолчанию не задана).

## 6. Простой, keepalive и срок жизни

После последнего запроса h2-соединения endpoint ждёт следующий запрос не дольше
`client_listener_timeout_secs` (по умолчанию 600 с). Запрос перезапускает
ожидание, поэтому клиент через случайные промежутки шлёт крошечный CONNECT на
`_check`; один HTTP/2 PING запросом не является. У туннелируемых TCP-соединений
`tcp_connections_timeout_secs` (по умолчанию неделя), у UDP 300 с. Срок жизни
TLS-соединения и его ротацию решает клиент; кода для них в endpoint'е нет. У
принятого сокета включён TCP keepalive.

```text
  client                                endpoint
    |-- CONNECT _check ----------------->|  wait for next request restarts
    |<--------------- 200 (END_STREAM) --|  (client_listener_timeout_secs)
    ...random pause...
    |-- CONNECT _check ----------------->|
```

## 7. Чего нет на сервере

- Ротация ключа между серверами и именами SNI (клиент, 9а): серверного кода нет.
  Каждый сервер ротации является обычным endpoint'ом.
- Срок жизни сессии, размер пула, интервалы между рукопожатиями: только клиент.
- Выбор TLS-профиля (Chrome 157, Firefox 160): только клиент. Endpoint лишь
  считает строку JA4, которую видит.

## 8. Совместимость

- Добавленные заголовки ответа являются обычными заголовками HTTP/2, а кадры DATA
  по 4096 байт укладываются в лимиты h2. В этом репозитории нет теста с официальным
  клиентом TrustTunnel; этот пункт здесь не проверен.
- Клиент с адреса из `decoy_only_ips_file` получает отказ при любых учётных
  данных.
- У ключей конфигурации, добавленных форком, значения по умолчанию сохраняют
  поведение upstream (`decoy_only_ips_file` не задан, `cattail` не задан,
  `xhttp_enable = false`).
